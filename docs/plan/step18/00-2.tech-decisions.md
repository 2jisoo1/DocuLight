# Step 18: 기술 결정 기록

## ADR-001: 활동 로거를 미들웨어가 아닌 유틸 함수로 구현

### 컨텍스트
활동 로그를 기록하는 방법으로 (A) Express 미들웨어 vs (B) 유틸 함수 직접 호출 선택.

### 결정: (B) 유틸 함수 직접 호출

### 근거
- 미들웨어는 req/res 수준에서만 동작 → 비즈니스 맥락(누가 어떤 문서를, 어떤 도구를) 접근 어려움
- 각 라우트/컨트롤러 내부에서 직접 호출해야 사용자 정보, 문서 경로, 도구명 등 구체적 정보 기록 가능
- 기존 `request-logger.js` 미들웨어는 HTTP 수준 로그로 유지 (중복 아님)

### 트레이드오프
- (+) 카테고리별 맥락 정보 풍부
- (+) 기존 코드에 1~2줄 추가로 통합 가능
- (-) 각 라우트에 수동 삽입 필요 (누락 가능성)

## ADR-002: 기존 logger.js 재사용 (새 로거 생성 안 함)

### 컨텍스트
활동 로그 전용 로거를 새로 만들지, 기존 `src/utils/logger.js` 인스턴스를 재사용할지.

### 결정: 기존 logger 재사용

### 근거
- 기존 logger가 이미 날짜별 파일 분리, maxDays 보존, 디렉토리 관리를 처리
- 동일 로그 파일(`DocuLight-YYYYMMDD.log`)에 통합하여 시간순 추적 용이
- `activity-logger.js`는 기존 logger를 감싸서 포맷팅만 담당하는 thin wrapper

### 트레이드오프
- (+) 중복 코드 없음, 로그 파일 관리 일원화
- (-) 활동 로그만 별도 파일 분리 불가 (필요 시 향후 확장)

## ADR-003: 직접 가입 시 이메일 인증 생략

### 컨텍스트
`signupMode: "self"` 모드에서 이메일 인증을 거칠지 여부.

### 결정: 이메일 인증 생략, 즉시 계정 생성

### 근거
- 사용자 요구사항: "직접 가입" = 즉시 사용 가능
- `allowedEmailDomains`로 도메인 제한이 가능하므로 무분별 가입 방지됨
- 승인 모드(`approval`)에서는 기존 이메일 인증 유지

### 트레이드오프
- (+) 가입 UX 단순화 (한 단계에 완료)
- (-) 가짜 이메일로 가입 가능 → 도메인 제한으로 완화

## ADR-004: signupMode 기본값을 "approval"로 설정

### 컨텍스트
`signupMode` 미설정 시 기본 동작.

### 결정: 기본값 `"approval"`

### 근거
- 하위 호환성: Step 17에서는 항상 승인 기반이었으므로 동일 동작 유지
- 보안 측면: 관리자가 명시적으로 `"self"`를 선택해야 직접 가입 활성화
