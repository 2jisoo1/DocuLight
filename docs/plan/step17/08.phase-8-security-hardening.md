# Phase 8: Rate Limiting + 보안 강화

## 목표

보안 관련 요구사항(Rate Limiting, 브루트포스 방어, 민감 정보 로깅 방지 등)을 구현하여 보안 체크리스트를 완성한다.

## 선행 조건

- Phase 7 완료 (가입 요청 워크플로우)

## 아키텍처 참조

- SRS NFR-17-003: 브루트포스 방어
- SRS NFR-17-007: Rate Limiting
- SRS 부록 B: 보안 체크리스트

## 구현 체크리스트

### 8.1 의존성 추가

- [ ] `package.json`에 `express-rate-limit` 추가
- [ ] `npm install express-rate-limit`

### 8.2 Rate Limiting 미들웨어 구현

- [ ] `src/middleware/rate-limiter.js` 생성
- [ ] **로그인 Rate Limiter**:
  - 동일 IP에서 1분에 10회
  - 적용: `POST /api/auth/login`
  - 초과 시: 429 `TOO_MANY_REQUESTS` + `Retry-After` 헤더
- [ ] **가입 요청 Rate Limiter**:
  - 동일 IP에서 5분에 3회
  - 적용: `POST /api/auth/signup`
- [ ] **이메일 인증 Rate Limiter**:
  - 동일 IP에서 1시간에 3회
  - 적용: `GET /api/auth/verify/:token`
- [ ] 각 limiter를 해당 라우트에 적용
- [ ] 검증: 제한 초과 시 429 응답 + Retry-After 헤더

### 8.3 브루트포스 방어 강화

- [ ] 이미 Phase 2에서 구현한 로그인 실패 카운터 + 잠금을 검증
- [ ] 잠금 상태에서도 동일한 에러 메시지 반환 (타이밍 공격 방지)
  - 잠긴 계정 로그인 시도: `bcrypt.compare()` 실행 후 거부 (일정한 응답 시간)
  - 또는 일정 시간 대기 후 응답 (일관된 응답 시간)
- [ ] 검증: 잠금/미잠금 상태의 응답 시간 차이가 유의미하지 않음

### 8.4 민감 정보 로깅 방지

- [ ] 로그에 패스워드, user-key 등이 기록되지 않도록 확인
- [ ] 요청 로깅 미들웨어에서 `password`, `newPassword`, `currentPassword` 필드 마스킹
- [ ] `X-API-Key`, `Authorization` 헤더값 마스킹 (앞 8자만 로그)
- [ ] 에러 로그에 스택 트레이스 내 민감 정보 없음 확인
- [ ] 검증: 로그 파일에 평문 패스워드/키 없음

### 8.5 패스워드 평문 메모리 정리

- [ ] 패스워드 변수 사용 후 빈 문자열로 덮어쓰기
- [ ] `req.body.password = ''; req.body.currentPassword = '';` 등
- [ ] 검증: bcrypt.compare/hash 호출 후 원본 패스워드 변수 덮어쓰기

### 8.6 데이터 파일 보안

- [ ] `data/` 디렉토리 생성 시 퍼미션 0700 적용 (Unix)
- [ ] JSON 파일 저장 시 퍼미션 0600 적용 (Unix)
- [ ] Windows 환경 고려: `fs.chmod`가 지원하지 않으므로 로그 경고만 출력
- [ ] 검증: `ls -la data/` 결과 확인 (Unix)

### 8.7 보안 체크리스트 검증

- [ ] 패스워드: bcrypt cost 12, 평문 미저장
- [ ] 세션 토큰: 256-bit 랜덤, httpOnly, SameSite=Strict
- [ ] user-key: 256-bit 랜덤, SHA-256 해시 저장, timing-safe 비교
- [ ] 이메일 인증 토큰: 256-bit 랜덤, 24시간 만료, 1회용
- [ ] 브루트포스: 5회 실패 시 15분 잠금
- [ ] Rate Limiting: 로그인, 가입, 인증 요청
- [ ] CSRF: SameSite 쿠키 + 헤더 기반 API 인증
- [ ] XSS: 기존 DOMPurify 유지
- [ ] 에러 메시지: 이메일/패스워드 오류 구분 안 함
- [ ] 로그: 민감 정보 마스킹

## 테스트 시나리오

### 정상 케이스

**Given**: 동일 IP에서 9회 로그인 시도 (성공/실패 무관)
**When**: 10번째 로그인 시도
**Then**: 정상 처리

**Given**: 동일 IP에서 10회 로그인 시도
**When**: 11번째 로그인 시도
**Then**: 429 응답, Retry-After 헤더 포함

### 예외 케이스

**Given**: 잠긴 계정에 올바른 패스워드로 로그인
**When**: 잠금 기간 내 시도
**Then**: 429 `TOO_MANY_ATTEMPTS` (올바른 패스워드여도 거부)

### 경계값 테스트

**Given**: Rate Limit 직전 (10회 중 10번째)
**When**: 정확히 1분 후 재시도
**Then**: 카운터 리셋, 정상 처리

## 회귀 테스트 체크리스트

- [ ] 정상적인 로그인/로그아웃 흐름에 Rate Limiting 영향 없음
- [ ] 정상적인 API 사용에 Rate Limiting 영향 없음
- [ ] 기존 로그 형식 유지 (민감 정보만 마스킹)
