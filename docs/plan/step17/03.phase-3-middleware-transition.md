# Phase 3: 인증 미들웨어 전환

## 목표

기존 apiKey 기반 인증 미들웨어를 user-key 기반으로 전환하고, 요청 경로와 인증 설정에 따른 로그인 필요 판단 로직을 구현한다.

## 선행 조건

- Phase 2 완료 (로그인/세션 시스템, UserStore 사용 가능)

## 아키텍처 참조

- [00-1.architecture.md](00-1.architecture.md): API/MCP user-key 인증 시퀀스, 권한 계층
- SRS FR-17-003: 로그인 필요 판단 로직
- SRS FR-17-006: User-Key 관리

## 구현 체크리스트

### 3.1 auth.js 전면 재작성

- [ ] `src/middleware/auth.js` 전면 재작성
- [ ] **기존 동작** (현재):
  ```javascript
  // req.header('X-API-Key') === config.apiKey
  ```
- [ ] **새 동작**:
  1. user-key 추출: `X-API-Key` 헤더 또는 `Authorization: Bearer` 헤더
  2. user-key → SHA-256 해싱
  3. `UserStore.findByUserKeyHash(hash)` → 사용자 조회
  4. `user.status === 'disabled'` → 401 `ACCOUNT_DISABLED`
  5. 사용자의 `groupId` → `GroupStore.findById(groupId)` → 권한 조회
  6. `req.apiUser = { userId, email, groupId, permissions }` 설정
  7. `next()`
- [ ] `crypto.timingSafeEqual()` 사용: user-key 해시 비교 시 (타이밍 공격 방지)
- [ ] 검증: 유효한 user-key → 통과, 잘못된 key → 401, 비활성 계정 → 401

## 테스트 시나리오

### 정상 케이스

**Given**: 활성 사용자의 user-key가 `abc123...`
**When**: `GET /api/tree` with `X-API-Key: abc123...` (requireReadLogin=true)
**Then**: 200 정상 응답

**Given**: `requireReadLogin = false`
**When**: 인증 없이 `GET /api/tree` 접속
**Then**: 200 정상 응답

### 예외 케이스

**Given**: 비활성화된 사용자의 user-key
**When**: `X-API-Key` 헤더로 API 호출
**Then**: 401 `ACCOUNT_DISABLED`

**Given**: read 권한만 있는 사용자
**When**: `POST /api/upload` with user-key
**Then**: 403 `INSUFFICIENT_PERMISSION`

### 경계값 테스트

**Given**: `Authorization: Bearer <key>` 형식 사용
**When**: API 호출
**Then**: `X-API-Key` 헤더와 동일하게 인증 성공
