# 기술 결정 기록 (ADR)

## ADR-001: 프로젝트 인덱스 저장 방식

**결정**: 메모리 캐시 (서버 시작 시 구축, 파일 변경 시 갱신)

**근거**:
- 문서 수가 수천 개 미만으로 예상 → DB 불필요
- tree-service의 기존 디렉토리 스캔 로직 재활용 가능
- config-watcher가 이미 파일 변경 감지 → 인덱스 갱신 트리거 가능

**대안 검토**:
- SQLite: 과도한 의존성 추가
- JSON 파일 캐시: 파일 I/O 오버헤드, 동기화 문제

## ADR-002: 퍼지 매칭 알고리즘

**결정**: 단계적 매칭 (exact → case-insensitive → contains → Levenshtein)

**근거**:
- 외부 라이브러리 의존 최소화 (CLAUDE.md 원칙: simplicity first)
- Levenshtein은 간단한 자체 구현 (20줄 이내)
- 한글 검색 지원 필요 → 단순 contains가 효과적

**구현 방식**:
```javascript
// 1순위: 정확 일치 (score: 1.0)
// 2순위: 대소문자 무시 (score: 0.95)
// 3순위: aliases 매칭 (score: 0.90)
// 4순위: 제목 포함 (score: 0.80)
// 5순위: 부분 문자열 (score: 0.70)
// 6순위: 편집 거리 ≤ 2 (score: 0.50)
```

## ADR-003: 코드 블록 추출 방식

**결정**: 정규식 기반 fenced code block 파싱

**근거**:
- 마크다운 AST 파서(remark 등) 도입은 과도
- fenced code block (```` ``` ````)만 지원하면 충분
- 기존 SectionExtractor의 heading 분할 로직과 조합

**파싱 패턴**:
```javascript
/^```(\w*)\n([\s\S]*?)^```/gm
```

## ADR-004: 버전 해석 방식

**결정**: 디렉토리 구조 + frontmatter 하이브리드

**근거**:
- 기존 디렉토리 기반 문서 구조와 호환
- frontmatter는 이미 DocLight가 지원 (frontmatter-service.js)
- `version` 필드를 frontmatter에 추가하는 것이 가장 비침습적

**우선순위**:
1. 디렉토리명에 버전 패턴 (`v1.0`, `v2.0`)
2. frontmatter `version` 필드
3. 없으면 버전 없음 (기본)

## ADR-005: 자동 호출 가이드 방식

**결정**: MCP serverInstructions + 문서화

**근거**:
- Claude Code는 MCP 서버의 `serverInstructions`를 시스템 프롬프트에 포함
- context-mcp.js의 `initialize` 응답에 instructions 추가 가능
- 별도 코드 변경 없이 가이드만으로도 효과적
