# MCP Streamable HTTP 스펙 Gap 분석

## 메타데이터

- 분석 일자: 2026-06-01
- 분석 대상: DocuLight MCP HTTP 구현
- 기준 문서: `docs/research/2026-06-01-mcp-streamable-http-spec.md`
- 주요 구현 파일:
  - `src/routes/mcp.js`
  - `src/routes/context-mcp.js`
  - `src/app.js`
  - `src/middleware/ip-whitelist.js`
  - `README.md`
  - `docs/mcp/doc/mcp.md`

## 결론

현재 구현은 `POST /mcp`에서 JSON-RPC 2.0 request를 처리하는 단순 HTTP MCP-like endpoint이다. 최신 MCP 2025-11-25의 Streamable HTTP transport로 보기에는 lifecycle, GET endpoint, notification 처리, protocol version header, Origin 검증, 문서화에서 주요 gap이 있다.

단, 모든 tool call을 SSE로 streaming해야 하는 것은 아니다. 이 프로젝트가 최신 Streamable HTTP 최소 구현을 목표로 한다면, POST request에 대해서는 기존처럼 `application/json` 단일 응답을 유지할 수 있다. 우선 필요한 변경은 "SSE 구현"보다 "Streamable HTTP transport의 HTTP/lifecycle 규칙 준수"이다.

## Gap 목록

### GAP-1. `/mcp`가 Streamable HTTP 단일 endpoint 요구를 충족하지 않음

**Severity**: High

**Spec 기준**: Streamable HTTP 서버는 단일 MCP endpoint에서 `POST`와 `GET`을 지원해야 한다. GET은 SSE stream을 반환하거나, 서버가 SSE stream을 제공하지 않는 경우 `405 Method Not Allowed`를 반환해야 한다.

**현재 상태**:

- `router.post('/mcp', ...)`만 존재한다.
- `GET /mcp` 핸들러가 없다.
- 결과적으로 `GET /mcp`는 앱의 일반 404 handler로 떨어진다.

**영향**:

최신 Streamable HTTP client가 endpoint capability를 탐지하거나 server-to-client stream을 열기 위해 GET을 사용할 때, 스펙상 기대되는 `405`가 아니라 `404`를 받는다. 이는 "SSE 미지원 Streamable HTTP endpoint"와 "존재하지 않는 endpoint"를 구분하지 못하게 만든다.

**권장 조치**:

- `router.get('/mcp', ...)` 추가
- server-to-client SSE를 당장 구현하지 않을 경우 `405 Method Not Allowed` 반환
- `Allow: POST, GET` 또는 `Allow: POST` 정책은 구현 결정에 맞춰 명확히 설정

### GAP-2. `notifications/initialized`를 처리하지 않음

**Severity**: High

**Spec 기준**: 성공적인 `initialize` 후 클라이언트는 `notifications/initialized` notification을 보내야 한다. Streamable HTTP에서 notification을 서버가 수락하면 HTTP `202 Accepted`와 빈 body를 반환해야 한다.

**현재 상태**:

- method가 없으면 JSON-RPC error를 반환한다.
- `notifications/initialized` method case가 없다.
- default branch에서 `Method not found` JSON-RPC error를 반환한다.

**영향**:

정상 lifecycle을 따르는 client가 initialized notification을 보내면 서버가 오류로 처리한다. 최신 MCP lifecycle과의 상호운용성이 깨진다.

**권장 조치**:

- `id`가 없는 notification을 JSON-RPC request와 구분
- `notifications/initialized` 수락 시 HTTP `202`와 빈 body 반환
- lifecycle state를 저장하지 않는 stateless 최소 구현이라도 notification 수락은 필요

### GAP-3. 초기화가 첫 상호작용이라는 lifecycle 규칙을 강제하지 않음

**Severity**: High

**Spec 기준**: initialization phase는 client-server의 첫 상호작용이어야 한다. Operation phase에서는 협상된 protocol version과 capability만 사용해야 한다.

**현재 상태**:

- `tools/list`, `tools/call`을 `initialize` 없이 바로 호출할 수 있다.
- 요청별 또는 session별 initialized 상태가 없다.
- capability negotiation 결과를 operation에 반영하지 않는다.

**영향**:

엄격한 MCP client/server 상호운용성 검증에서 lifecycle 위반으로 분류될 수 있다. 향후 resources, prompts, tasks, logging 등 capability가 늘면 더 큰 계약 불일치가 생긴다.

**권장 조치**:

- 최소 구현: `initialize` 이전의 request는 `initialize`와 ping 정도만 허용
- stateful 구현: `MCP-Session-Id`를 발급하고 session별 initialized 상태 추적
- stateless 구현: header 또는 lightweight state 전략을 명확히 설계하되, `notifications/initialized`는 수락

### GAP-4. protocol version negotiation이 구현되지 않음

**Severity**: High

**Spec 기준**: client는 `initialize.params.protocolVersion`을 보내야 한다. 서버가 해당 version을 지원하면 같은 version으로 응답해야 하며, 지원하지 않으면 서버가 지원하는 다른 version으로 응답해야 한다.

**현재 상태**:

- 서버는 client params를 확인하지 않는다.
- 항상 `protocolVersion: "2024-11-05"`를 반환한다.
- `2025-11-25` Streamable HTTP 지원 여부가 코드로 표현되어 있지 않다.

**영향**:

2025-11-25 client는 서버 응답 version이 지원 목록과 맞지 않으면 연결을 끊을 수 있다. 최신 HTTP transport를 지원한다고 문서화하기 어렵다.

**권장 조치**:

- 지원 version 목록 정의
- `initialize.params.protocolVersion` 파싱
- 지원 version이면 동일 version 반환
- 미지원 version이면 명확한 fallback 또는 JSON-RPC initialization error 정책 결정

### GAP-5. `MCP-Protocol-Version` header를 처리하지 않음

**Severity**: High

**Spec 기준**: HTTP 후속 요청에는 `MCP-Protocol-Version` header가 포함되어야 한다. invalid 또는 unsupported version이면 서버는 `400 Bad Request`를 반환해야 한다.

**현재 상태**:

- 코드에서 `MCP-Protocol-Version` header를 읽지 않는다.
- invalid/unsupported version에 대한 `400` 응답이 없다.
- header가 없는 경우의 backwards compatibility 정책도 없다.

**영향**:

version-aware client와의 상호운용성이 약하고, 향후 여러 protocol version을 동시에 지원할 때 behavior가 불명확하다.

**권장 조치**:

- `req.header('MCP-Protocol-Version')` 검증 middleware 또는 route guard 추가
- `initialize` 이후 후속 request에 대해 negotiated version 또는 supported fallback 검증
- header 누락 시 `2025-03-26` fallback을 적용할지, 기존 `2024-11-05` 호환 모드를 별도로 둘지 결정

### GAP-6. JSON-RPC notification/response의 HTTP semantics가 맞지 않음

**Severity**: Medium

**Spec 기준**: POST body가 JSON-RPC notification 또는 response이면, 서버가 수락할 때 HTTP `202 Accepted`와 빈 body를 반환해야 한다.

**현재 상태**:

- 모든 입력에서 `method`를 요구한다.
- `id`가 없는 notification도 일반 request처럼 처리하려고 한다.
- JSON-RPC response 입력은 `method is required` error로 처리된다.

**영향**:

`notifications/initialized`, cancellation notification, client-side response를 정상적으로 수락하지 못한다.

**권장 조치**:

- JSON-RPC message type 판별 함수 추가
- notification/response 수락 시 `res.status(202).end()`
- 알 수 없는 notification은 정책에 따라 202로 무시하거나 400으로 거부하되, JSON-RPC request error와 구분

### GAP-7. `Accept` header 처리/검증이 없음

**Severity**: Medium

**Spec 기준**: Streamable HTTP client는 POST에 `Accept: application/json, text/event-stream`을 포함해야 한다. request 응답은 `application/json` 또는 `text/event-stream`이어야 한다.

**현재 상태**:

- route는 `Accept` header를 확인하지 않는다.
- 응답은 Express `res.json`으로 사실상 `application/json`이지만, transport 요구사항으로 명시적으로 관리되지 않는다.
- 기존 테스트 helper도 `Accept` header를 보내지 않는다.

**영향**:

엄격한 conformance test에서는 client request shape와 server content negotiation이 검증되지 않는다. 다만 서버가 단일 JSON 응답만 제공하는 최소 구현이라면 이 gap은 High는 아니다.

**권장 조치**:

- POST request에서 `Accept` header를 검증하거나 최소 경고/compatibility mode를 둔다.
- response content type을 명시적으로 `application/json`으로 유지
- 테스트에 `Accept: application/json, text/event-stream` 추가

### GAP-8. `Origin` 검증이 없음

**Severity**: High

**Spec 기준**: Streamable HTTP 구현 시 서버는 incoming connection의 `Origin` header를 검증해야 하며, header가 존재하고 invalid이면 HTTP `403 Forbidden`으로 응답해야 한다.

**현재 상태**:

- IP whitelist middleware는 존재하지만 Origin 검증과는 다르다.
- `Origin` header allowlist 또는 same-origin 검증이 없다.
- 기본 bind가 `0.0.0.0`이다.

**영향**:

로컬 MCP 서버가 브라우저 기반 DNS rebinding 공격에 노출될 수 있다. IP whitelist가 설정되어 있지 않은 기본/개발 환경에서는 특히 위험하다.

**권장 조치**:

- MCP endpoint 전용 Origin 검증 middleware 추가
- allowed origins 설정 도입
- 로컬 기본 bind를 `127.0.0.1`로 바꾸거나 MCP 활성화 시 경고/명시 설정 요구

### GAP-9. local bind 권고와 기본값이 어긋남

**Severity**: Medium

**Spec 기준**: 로컬 실행 서버는 `0.0.0.0`보다 `127.0.0.1`에 bind하는 것이 권고된다.

**현재 상태**:

- 기본 host가 `0.0.0.0`이다.
- config example에는 일반 서버 port 설명은 있으나 MCP local bind 위험 설명은 없다.

**영향**:

개발자가 기본값으로 실행하면 LAN 또는 컨테이너 네트워크에 MCP endpoint가 노출될 수 있다.

**권장 조치**:

- 기본 host를 `127.0.0.1`로 변경하는 방안 검토
- 외부 공개가 필요한 배포는 config로 명시하게 한다.
- 변경이 호환성에 부담이면 MCP docs에 보안 경고와 권장 설정을 추가한다.

### GAP-10. 문서가 최신 Streamable HTTP가 아니라 `POST /mcp` legacy 형태로 설명됨

**Severity**: Medium

**Spec 기준**: 최신 HTTP MCP 설명은 Streamable HTTP, 단일 endpoint, POST/GET, lifecycle, protocol header, Origin 검증을 포함해야 한다.

**현재 상태**:

- README는 `POST /mcp`, `Transport: HTTP`, `Method: POST`로만 설명한다.
- MCP 문서는 `Endpoint: POST /mcp`, `MCP Version: 2024-11-05`, `Authentication: Not required`로 설명한다.
- Claude Code 예시는 `curl` command 기반 설정도 포함되어 있어 최신 HTTP transport 설명과 혼재되어 있다.

**영향**:

사용자는 프로젝트가 최신 Streamable HTTP MCP를 지원한다고 오해하거나, 반대로 최신 client 등록에 필요한 헤더/lifecycle 정보를 얻지 못한다.

**권장 조치**:

- 현 상태를 "legacy/simple HTTP JSON-RPC MCP endpoint"로 명확히 표시
- Streamable HTTP 구현 후 문서를 `MCP Version: 2025-11-25`, `Transport: Streamable HTTP`로 갱신
- `GET /mcp`는 SSE 미지원 시 `405`라고 문서화
- 인증 설명을 "read는 설정 의존, write는 X-API-Key 필요"로 정정

### GAP-11. `/context`를 MCP endpoint처럼 볼 경우 Streamable HTTP와 의미가 충돌함

**Severity**: Medium

**Spec 기준**: Streamable HTTP의 GET은 server-to-client SSE stream 또는 `405`를 의미한다.

**현재 상태**:

- `GET /context`는 REST-like info/list/read/search API이다.
- `POST /context`는 JSON-RPC 2.0 MCP-like API이다.

**영향**:

`/context`를 MCP transport endpoint로 문서화하면 최신 Streamable HTTP GET 의미와 충돌한다. REST helper API로는 유용하지만, MCP endpoint로는 구분이 필요하다.

**권장 조치**:

- `/context`는 "context REST helper + JSON-RPC-like endpoint"로 명확히 분류
- 최신 MCP endpoint로 유지하려면 `/context`의 GET semantics를 바꾸거나 별도 path를 둔다.

## 우선순위 제안

### Phase 1. 최소 Streamable HTTP conformance

1. `GET /mcp` 추가 및 SSE 미지원 시 `405` 반환
2. notification/response 입력 판별 및 `202 Accepted` 처리
3. `notifications/initialized` 수락
4. `initialize.params.protocolVersion` 기반 version negotiation
5. `MCP-Protocol-Version` header 검증
6. `Origin` 검증

### Phase 2. Lifecycle state와 보안 강화

1. `MCP-Session-Id` 발급 여부 결정
2. session을 발급한다면 initialized state와 종료/404 규칙 구현
3. 기본 bind 및 MCP-specific security config 정리
4. request timeout/cancellation 정책 정리

### Phase 3. 선택 기능

1. POST response SSE streaming
2. GET server-to-client SSE stream
3. SSE event id, retry, Last-Event-ID 기반 resumability
4. tasks/progress/cancellation 고급 기능

## 검증 항목 제안

| 테스트 | 기대 결과 |
| --- | --- |
| `GET /mcp` with `Accept: text/event-stream` | SSE 미지원이면 HTTP 405 |
| `POST /mcp` initialize with `protocolVersion: 2025-11-25` | 같은 version 반환 또는 명확한 supported version 반환 |
| `POST /mcp` notifications/initialized | HTTP 202, empty body |
| `POST /mcp` tools/list before initialize | lifecycle 정책에 맞는 오류 또는 session 요구 |
| invalid `MCP-Protocol-Version` | HTTP 400 |
| invalid `Origin` | HTTP 403 |
| POST notification with no `id` | HTTP 202 |
| POST JSON-RPC response body | HTTP 202 또는 명확한 400 |
| POST request with current simple response mode | `Content-Type: application/json` |

## 최종 판단

현재 구현은 기존 클라이언트나 curl 기반 direct HTTP 호출에는 유용하지만, 최신 MCP 2025-11-25 Streamable HTTP transport를 준수한다고 보기 어렵다. 최소 준수 목표라면 SSE 자체보다 `GET /mcp`, notification `202`, lifecycle, version header, Origin 검증을 먼저 구현하는 것이 맞다.
