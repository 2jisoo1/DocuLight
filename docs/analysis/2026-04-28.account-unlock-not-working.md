# 계정 잠금 해제 미작동 분석

## 증상
로그인 실패가 누적되어 계정이 잠긴 상태(lockedUntil 시간 설정됨)에서, 어드민 페이지의 "잠금 해제" 버튼을 눌러도 실제로 그 계정의 잠금이 해제되지 않는 문제.

## 잠금 메커니즘 (저장 구조)

### 사용자 데이터 구조 (src/stores/user-store.js)
```
user object:
{
  id: UUID,
  email: string,
  passwordHash: bcrypt_hash,
  groupId: UUID,
  failedLoginCount: number (초기값: 0),
  lockedUntil: ISO8601 | null (초기값: null),
  status: 'active' | 'disabled',
  lastLoginAt: ISO8601 | null,
  createdAt: ISO8601,
  updatedAt: ISO8601
}
```

### 잠금 판정 로직 (src/controllers/auth-controller.js, login 함수)
라인 111-117: lockedUntil과 현재 시간을 비교하여 잠금 여부 판정
- 조건: user.lockedUntil이 존재하고 시간이 미래인 경우 잠금
- 응답: 429 TOO_MANY_ATTEMPTS

### 잠금 발생 로직 (src/stores/user-store.js, incrementFailedLogin)
라인 249-258: 로그인 실패 5회(MAX_FAILED_ATTEMPTS) 이상 시 잠금 설정
- failedLoginCount 증가
- 5회 이상 시 lockedUntil을 15분(LOCK_DURATION_MS) 뒤로 설정
- 데이터 저장: await this.store.save()

## 잠금 해제 흐름 (frontend → backend)

### 1. Frontend 트리거 (public/js/admin.js)
라인 1879-1884: 어드민 UI에서 "잠금 해제" 버튼 클릭
- AdminAPI.unlockUser(user.id) 호출
- 응답 후 성공 메시지 표시

### 2. API 호출 (public/js/admin.js, AdminAPI)
라인 253-256: HTTP POST 요청
- 엔드포인트: /api/admin/users/{id}/unlock
- 메서드: POST
- 인증: 포함

### 3. 라우팅 (src/routes/admin-api.js)
라인 232: 라우트 정의
- 경로: /users/:id/unlock
- 미들웨어: adminAuth(), requirePermission('superuser')
- 핸들러: userController.unlockUser

### 4. Backend 핸들러 (src/controllers/admin/admin-user-controller.js)
라인 178-191: unlockUser 함수
- 사용자 ID로 기존 사용자 조회
- 존재하지 않으면 404 반환
- userStore.resetFailedLogin(id) 호출
- 성공 응답: { "success": true }

### 5. 잠금 해제 실행 (src/stores/user-store.js)
라인 260-267: resetFailedLogin 함수
- idIndex에서 사용자 조회
- failedLoginCount = 0으로 초기화
- lockedUntil = null로 설정
- 데이터 저장: await this.store.save()

## 원인 분석 (가설)

### 현재 코드는 기술적으로 정상임
1. 잠금 필드: lockedUntil 필드 설정 및 초기화 로직이 동일
2. 저장 메커니즘: 각 작업마다 await this.store.save() 호출로 파일 저장
3. 사용자 식별: id 파라미터를 일관되게 사용

### 실제 증상의 원인 가능성들:

#### 가능성 1: UI 캐싱 문제 (가장 높은 확률)
- 문제: 어드민이 "잠금 해제" 버튼을 누른 후 백엔드에서는 정상 처리되지만, UI가 이전 상태를 계속 표시
- 원인: API 응답 후 UI가 자동으로 사용자 목록을 다시 불러오지 않음
- 증거: admin.js 라인 1879-1883에서 성공 메시지만 표시하고 목록 갱신 코드 없음
  - 비교: updateUser에는 setTimeout(() => this.loadTab('users'), 700) 있음 (라인 1858)
  - unlockUser와 resetPassword에는 없음 (라인 1871-1877, 1879-1883)

#### 가능성 2: 저장 실패 (동시성 문제)
- 문제: 파일 기반 저장소에서 동시 요청 시 마지막 저장만 반영
- 원인: BaseJsonStore가 동시 쓰기 보호 메커니즘 없음
- 확인 필요: src/stores/base-json-store.js 검토

#### 가능성 3: 에러 처리 누락
- 문제: resetFailedLogin 또는 저장 중 에러 발생 시 클라이언트에 알려지지 않음
- 원인: unlockUser에서 에러 처리 없음 (라인 189-190)

#### 가능성 4: 사용자 객체 메모리 동기화 미흡
- 문제: 메모리 인덱스의 사용자 객체가 실제 저장된 상태와 불일치
- 원인: 동시성 문제나 메모리 누수로 인한 객체 중복

#### 가능성 5: 클라이언트 캐시
- 문제: 브라우저가 API 응답을 캐싱하여 이전 사용자 정보를 계속 표시
- 원인: HTTP 캐시 헤더 설정

## 검증 방법

### 1. 직접 파일 확인
```
cat data/users.json | jq '.users[] | select(.email=="test@example.com") | {email, failedLoginCount, lockedUntil}'
```
- 파일상 lockedUntil이 실제로 null인지 확인

### 2. 로그 분석
```
grep -i unlock logs/activity.log
```
- unlock 작업 기록 확인

### 3. UI 새로고침 테스트
1. 잠긴 계정으로 로그인 시도
2. 어드민에서 "잠금 해제" 클릭
3. F5로 전체 페이지 새로고침
4. 잠긴 계정으로 다시 로그인 시도

### 4. 개발자 도구 API 확인
- F12 → Network 탭
- /api/admin/users/{id}/unlock 요청 및 응답 확인
- 응답이 { "success": true }인지 확인

### 5. 데이터 파일 시간 확인
```
jq '.users[] | select(.email=="test@example.com") | {email, updatedAt, lockedUntil}' data/users.json
```
- updatedAt이 해제 시간과 일치하는지 확인

파일: src/stores/base-json-store.js
수정: 파일 쓰기 잠금 메커니즘 또는 원자적 저장
목적: 동시 요청 시 데이터 무결성 보장

### 4. UI에 잠금 상태 표시 (감지 강화)

목적: 어드민이 시각적으로 잠금 상태 확인 가능

### 5. 로그 추가 (디버깅 지원)
파일: src/stores/user-store.js resetFailedLogin 함수
수정: 전후 상태 로깅
목적: 실제 변경이 일어났는지 확인 가능

## 추가 고려사항

### 보안
- 잠금 해제는 superuser 권한만 가능 (현재 정상)
- 해제 작업 로그 기록 필요 (현재 누락)

### 사용성
- 어드민이 누가 잠겨있는지 한눈에 알 수 있도록 표시 필요
- 잠금 해제 후 자동 반영이 되지 않아 혼동 유발 가능

### 설계
- lockedUntil 시간 만료 후 자동 해제 메커니즘 확인 필요
- 현재는 로그인 시도 시에만 판정하므로 자동 해제 미구현으로 보임
